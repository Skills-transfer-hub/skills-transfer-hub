# Research: State & Config Foundation

**Phase 0 output for `specs/005-state-config-foundation`**

All NEEDS CLARIFICATION items from Technical Context resolved. No external research tasks
were required — all decisions are derivable from the existing codebase and constitution.

---

## Decision 1: Schema detection strategy

**Decision**: Detect v1 by the absence of a `schema_version` field in the JSON. Use
`json.RawMessage` or a two-pass unmarshal (first into a `map[string]json.RawMessage` to
read the `schema_version` key, then into the typed struct).

**Rationale**: The current `ProjectProfile` and `InstalledResourceState` structs have no
`schema_version` field, so any file without it is definitionally v1. A `map` first-pass is
the idiomatic stdlib approach that avoids defining a separate "version probe" struct.

**Alternatives considered**:
- Separate version-probe struct (`type versionProbe struct { SchemaVersion int }`): simpler
  but requires an extra type definition per file type. Rejected for marginal benefit.
- File-existence heuristic (e.g., check for `providers` key): fragile — could misidentify
  hand-edited files. Rejected.

---

## Decision 2: Default provider ID during migration

**Decision**: Assign `id: "default"` to the single provider created during v1→v2 migration
of `project.json`. This value is only generated by the migration path; all future providers
are named by the user.

**Rationale**: "default" is semantically clear, not a URL or path (constitution II compliant),
and matches the common convention in multi-provider tools. Users who want to rename it can
run `loreskills init` again.

**Alternatives considered**:
- Derive from `repository_id` (e.g., `octo-org-skills-catalog`): clever but unpredictable;
  could collide if the user runs init for a second provider with a similar name. Rejected.
- Empty string: invalid per FR-008 (must be alphanumeric/hyphens/underscores). Rejected.

---

## Decision 3: SHA256 computation timing

**Decision**: Compute SHA256 over the final bytes written to disk (after `skillHeader` is
prepended for Markdown files). This is the "ground truth" that later integrity checks
(spec 006) will compare against.

**Rationale**: The spec states "SHA256 hashes are computed over the raw file bytes as written
to disk (after applying the skillHeader prefix if applicable)". Computing before prefix would
create a mismatch when the `status` command re-reads the file.

**Alternatives considered**:
- Hash the raw download content (before skillHeader): easier to verify against upstream, but
  breaks integrity checks that read the local file. Rejected.

## Decision 4: `resources` array population during migration

**Decision**: Migrate `lore-state.json` entries to v2 records and populate the `resources`
array in `project.json` v2 from those entries, assigning all to `provider_id: "default"`.
`resolved_version`, `previous_version`, and `installed_at` are set to empty/zero — they will
be populated on the next install or update.

**Rationale**: The current codebase tracks installed resources only in `lore-state.json`.
There is no install-time commit SHA, so it cannot be reconstructed. Leaving these fields
empty is honest and safe; spec 006 status command must tolerate empty `resolved_version`
(showing "version inconnue").

**Alternatives considered**:
- Leave `resources` empty and only add entries on future installs: simpler migration, but
  breaks US3 (pinning by `resource_name`) until each resource is reinstalled. Rejected.

## Decision 5: Migration atomicity

**Decision**: Use write-to-temp-then-rename for each migrated file on Unix/macOS.
On Windows (where cross-device rename fails), write directly after backup (same strategy
as the existing `ReplaceExecutableWithAsset` Windows path in `fs.go`).

**Rationale**: The spec requires original files be untouched on failure (FR-005). A
temp-then-rename pattern achieves this on Unix. Windows requires the same backup-then-write
fallback already implemented in the codebase.

**Alternatives considered**:
- Write directly with deferred rollback: error-prone if the process is killed mid-write.
  Rejected.

## Decision 6: `loreskills init` multi-provider UX

**Decision**: When `project.json` v2 already exists and the user runs `loreskills init`,
show the existing providers list and ask "Add a new provider?". If yes, prompt for a new
provider ID + config and append it to the providers array. Duplicate IDs are rejected
with an error message (US2 AC3).

**Rationale**: The spec says "loreskills init MUST support configuring multiple providers
by allowing the user to add provider entries sequentially" (FR-009). Re-using the init
command is the simplest UX that avoids a new `provider add` subcommand (deferred per
spec assumption §Assumptions).

**Alternatives considered**:
- Offer a "replace all" option: dangerous — would wipe working provider config. Rejected.
- `loreskills provider add`: cleaner long-term but out of scope for this spec. Deferred.

## Decision 7: Backward-compatible callers

**Decision**: Introduce a `ReadProjectConfigV2()` function alongside the existing
`ReadProjectProfile()`. During the transition, commands that only need single-provider
data can call a helper `PrimaryProvider(cfg ProjectConfigV2) ProviderEntry` that returns
the first provider. Existing callers are updated incrementally; `ReadProjectProfile()`
is not deleted in this spec.

**Rationale**: Hard-cutting over all callers at once risks regressions. The parallel
function approach lets each command be migrated and tested independently (SC-005).

**Alternatives considered**:
- Return `ProjectConfigV2` from the existing `ReadProjectProfile()`: would require
  renaming the return type, breaking existing callers in one shot. Rejected for this spec.

## Decision 8: Advisory File Lock — `O_CREATE|O_EXCL` approach

**Decision**: Implement advisory locking by creating `<stateDir>/.lore-state.lock` with
`os.OpenFile(..., os.O_CREATE|os.O_EXCL, 0o644)`, then closing the file immediately after
successful creation.
- If the call succeeds, the lock is represented by the presence of the lock file and a
  returned cleanup function removes it via `os.Remove`.
- If `O_EXCL` fails (file already exists), return an error immediately (fail-fast, FR-015).
- Lock file path: `<stateDir>/.lore-state.lock` (same directory as `lore-state.json`).

## Decision 9: `lore-state.json` vs `lore-state-v2.json` — Dual-File Approach

**Decision**: Keep `lore-state.json` as the legacy v1 file and `lore-state-v2.json` as
the canonical v2 file for this PR. `ReadInstalledStateV2` and `WriteInstalledStateV2`
continue to use `stateFileNameV2` (`lore-state-v2.json`); no consolidation to a single
state file is performed here.

**Background**: The codebase currently maintains two state files with distinct roles:
- `lore-state.json` — legacy v1 file, read by `ReadInstalledState` and used as migration input
- `lore-state-v2.json` — v2 file, read/written by `ReadInstalledStateV2` / `WriteInstalledStateV2`

This matches the implementation in the current PR. Rather than rewriting the legacy file
in place, the migration path preserves backward compatibility for v1 reads while using a
dedicated file for schema-versioned v2 state.

**Migration path**: On first access, `PromoteInstalledState` detects that `lore-state-v2.json`
is absent, reads `lore-state.json`, converts its content in memory, and writes the v2
representation to `lore-state-v2.json` atomically. The legacy `lore-state.json` is left
untouched. A progress line is emitted to stderr only when a v1 file is actually migrated
(FR-016).

**Alternatives considered**:
- Consolidate on `lore-state.json` immediately (in-place migration with backup): simpler
  long-term source-of-truth story but does not match this PR's implementation. Deferred.
- Keep both files and merge on read: complex and error-prone because it introduces multiple
  possible authorities for the same resource state. Rejected.

## Decision 10: Auto-Migration Entry Point

**Decision**: Inject a shared `runMigrations(stderr io.Writer) error` helper that is
called at the start of each `cmd/` command handler (before any state/config read).
`runMigrations` calls `MigrateProjectConfig(path, stderr)` and `MigrateInstalledState(path, stderr)`
in sequence; both are idempotent for already-v2 files (return immediately with zero I/O).

**Rationale**: FR-003 requires migration before the requested command executes. Making
it the first call in every handler guarantees no handler reads unmigrated files.
Idempotency means the cost is one `os.ReadFile` + JSON parse for already-v2 files
(negligible against FR migration time budget of 2 seconds for 50 resources).

**Alternatives considered**:
- Sentinel file (`.loreskills-migrated`): adds a file, is itself subject to corruption;
  idempotent migrate functions make the sentinel unnecessary. Rejected.
- Run only for install/update: `list` and `status` also read state; too narrow. Rejected.

## Decision 11: `resolved_version` / `previous_version` Population

**Decision**: `InstallCatalogEntryV2` accepts a new `resolvedVersion string` parameter.
Before upserting, `UpsertInstalledResourceV2` reads the existing record for the
`(resource_name, provider_id)` key and copies its `resolved_version` to `previous_version`.

**Rationale**: The commit SHA is returned by the HTTP client in `cmd/`; threading it as
a parameter preserves the fs/http layer separation (constitution IV). Reading the prior
version inside `UpsertInstalledResourceV2` before overwriting satisfies FR-012.

**Alternatives considered**:
- Have `cmd/` pre-read the state to capture previous version: duplicates logic already
  needed inside upsert. Rejected.
- Store previous version in the caller: leaks state management into `cmd/`. Rejected.
