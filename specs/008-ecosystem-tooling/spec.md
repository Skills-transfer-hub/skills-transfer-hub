# Feature Specification: Ecosystem Tooling

**Feature Branch**: `006-cli-product-roadmap`  
**Created**: 2026-04-23  
**Status**: Draft  
**Depends On**: [005-state-config-foundation](../005-state-config-foundation/spec.md), [006-resource-lifecycle](../006-resource-lifecycle/spec.md)  
**Blocks**: —  

## Context

This spec targets the experience of **skill authors** — developers who maintain skill
repositories — and enriches the experience of **skill consumers** during updates.

Three independent features are grouped here because they all relate to the skills
repository ecosystem rather than to the core install/update/remove workflow:

1. **`sth catalog init`**: auto-generates `SKILLS.md` from an existing directory
   structure instead of requiring manual authorship.
2. **`sth new <category>/<name>`**: scaffolds a new skill directory with the
   expected structure so new skills are immediately conformant.
3. **Changelog display on update**: surfaces `CHANGELOG.md` entries during `sth update`
   so consumers know what changed without visiting the upstream repository.

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Generate SKILLS.md from an Existing Skills Repository (Priority: P1)

A skills repository maintainer has dozens of skills organised as
`category/skill-name/SKILL.md`. They have been maintaining `SKILLS.md` by hand, which
is error-prone and tedious. Running `sth catalog init` generates a complete,
correctly formatted `SKILLS.md` from the directory structure — no manual editing needed.

**Why this priority**: `SKILLS.md` is the catalog that sth consumers depend on
to discover and install skills. A broken or stale catalog breaks every downstream
installation. Automation eliminates the maintenance burden and errors.

**Independent Test**: Create a directory structure with 3 categories and 2 skills each,
run `sth catalog init`, verify `SKILLS.md` lists all 6 skills grouped by category
and that `sth list` correctly parses it.

**Acceptance Scenarios**:

1. **Given** a repository with the `category/skill-name/SKILL.md` structure,
   **When** the maintainer runs `sth catalog init`, **Then** a `SKILLS.md` is
   created at the repository root listing all discovered skills grouped by category.
2. **Given** `SKILLS.md` already exists, **When** `sth catalog init` runs,
   **Then** the tool warns "SKILLS.md already exists" and asks for confirmation before
   overwriting; the `--force` flag skips the prompt.
3. **Given** the directory structure contains non-skill files alongside skill folders,
   **When** `sth catalog init` runs, **Then** only directories containing a
   `SKILL.md` file are included in the catalog; other entries are silently ignored.
4. **Given** a `SKILL.md` file contains a `description:` front-matter field,
   **When** `sth catalog init` runs, **Then** the description appears alongside
   the skill name in `SKILLS.md`.
5. **Given** `sth catalog init` runs in a directory with no valid skill folders,
   **When** the command completes, **Then** the tool exits with "No skills found matching
   the expected structure" and does not create an empty `SKILLS.md`.
6. **Given** `SKILLS.md` is generated by `sth catalog init`, **When** a consumer
   runs `sth list` against that repository, **Then** all generated entries are
   parseable and installable.

### User Story 2 — Scaffold a New Skill with `sth new` (Priority: P1)

A skills repository maintainer wants to add a new skill. Instead of copying an existing
skill folder and manually editing it, they run `sth new <category>/<name>` and
get a correctly structured skeleton with a `SKILL.md` template already filled with the
right front matter.

**Why this priority**: Inconsistent skill structures break catalog generation and
installation. A scaffold command eliminates structural errors at creation time.

**Independent Test**: Run `sth new prompts/code-review`, verify the directory
`prompts/code-review/` is created with a `SKILL.md` containing the required front matter
sections.

**Acceptance Scenarios**:

1. **Given** the user runs `sth new <category>/<name>`, **When** the command
   executes, **Then** the directory `<category>/<name>/` is created (including parent
   category directory if needed) with a `SKILL.md` file pre-populated with the
   required template structure.
2. **Given** the scaffolded `SKILL.md` is created, **When** the file is opened,
   **Then** it contains at minimum: a `name:` front matter field pre-filled with
   `<name>`, a `description:` front matter field with a placeholder, and a `## Usage`
   section.
3. **Given** the target directory already exists, **When** `sth new` is run,
   **Then** the tool exits with "Skill already exists at <path>" and does not overwrite.
4. **Given** the `<category>/<name>` argument contains invalid characters (spaces,
   special characters other than hyphens and underscores), **When** the command is run,
   **Then** the tool rejects the input with a clear error listing valid characters.
5. **Given** `sth new` is run in a directory that is not a skills repository
   (no `SKILLS.md` and no existing `category/skill` structure), **When** the command
   runs, **Then** the tool proceeds without error — scaffold works even in an empty repo.

### User Story 3 — See What Changed During an Update (Priority: P2)

A developer runs `sth update`. One of the updated bundles contains a
`CHANGELOG.md`. The tool displays the changelog entries that were added since the
previously installed version, so the developer immediately knows what changed without
visiting the upstream repository.

**Why this priority**: Silent updates break trust. Surfacing changelogs during update
gives consumers visibility and lets them decide whether to investigate further.

**Independent Test**: Install a resource at version v1 (which has a `CHANGELOG.md`),
update to v2 (which adds new entries), verify the new changelog entries are displayed
during `sth update`.

**Acceptance Scenarios**:

1. **Given** a bundle contains a `CHANGELOG.md` and the resource has a `previous_version`
   in state, **When** `sth update` installs a newer version, **Then** the
   changelog entries introduced since `previous_version` are printed under a
   "What's new in <resource-name>:" header.
2. **Given** a bundle contains a `CHANGELOG.md` but the resource has no `previous_version`
   (first install), **When** `sth install` runs, **Then** no changelog is shown
   (no "since" baseline exists).
3. **Given** a bundle does not contain a `CHANGELOG.md`, **When** `sth update`
   runs, **Then** no changelog section is shown and no error is emitted.
4. **Given** a `CHANGELOG.md` is present but larger than 50 KB, **When** `sth update`
   runs, **Then** only the first 50 KB is read and a note "(changelog truncated)" is
   appended to the display.
5. **Given** a `CHANGELOG.md` is malformed (not parseable as standard keepachangelog format),
   **When** `sth update` runs, **Then** a warning "Could not parse changelog for
   <resource-name>" is shown; the update itself is not blocked.
6. **Given** the `--json` flag is active during `sth update`, **When** a changelog
   is available, **Then** the changelog entries are included as a `changelog` field in
   the JSON output for that resource.

---

### Edge Cases

- What if `sth catalog init` finds two skills with the same name in different categories? → Both are included; they are distinguished by category prefix in `SKILLS.md`.
- What if a `SKILL.md` file is empty or has no front matter? → The skill is listed in `SKILLS.md` with an empty description; no error is thrown.
- What if `sth new` is called with only one path component (no `/`)? → Exit with "Invalid format: use <category>/<name>".
- What if `CHANGELOG.md` uses a non-standard format (not Keep a Changelog)? → Display the raw content up to the size limit with a note that automated parsing was not possible.
- What if a `sth catalog init`-generated `SKILLS.md` is later edited manually and then `catalog init` is re-run with `--force`? → Manual edits are lost; this is documented in the command's help text.

## Requirements *(mandatory)*

### Functional Requirements

**`sth catalog init`**

- **FR-001**: The command MUST scan the current directory for subdirectories matching the `<category>/<name>/SKILL.md` pattern.
- **FR-002**: The generated `SKILLS.md` MUST group skills by category and list each skill's name and description (from the `description:` front matter field, if present).
- **FR-003**: If `SKILLS.md` already exists, the command MUST prompt for confirmation before overwriting; `--force` MUST skip the prompt.
- **FR-004**: If no conforming skill directories are found, the command MUST exit with code 1 and a descriptive message without creating any file.
- **FR-005**: The generated `SKILLS.md` MUST be parseable by `sth list` — end-to-end compatibility is required.

**`sth new <category>/<name>`**

- **FR-006**: The command MUST create the directory `<category>/<name>/` (including parent directories) and a `SKILL.md` template file within it.
- **FR-007**: The scaffolded `SKILL.md` MUST contain at minimum: `name:` and `description:` front matter fields, and a `## Usage` section.
- **FR-008**: If the target directory already exists, the command MUST exit with code 1 and an error; it MUST NOT overwrite existing content.
- **FR-009**: The `<category>/<name>` argument MUST be validated to contain only alphanumeric characters, hyphens, underscores, and a single `/` separator. Invalid input MUST return a descriptive error.

**Changelog Display**

- **FR-010**: When `sth update` installs a newer version of a resource that contains `CHANGELOG.md`, and `previous_version` is set in state, the tool MUST display changelog entries introduced since `previous_version`.
- **FR-011**: The changelog parser MUST support the [Keep a Changelog](https://keepachangelog.com/) format (sections headed `## [<version>] - <date>` or `## [Unreleased]`). Other formats MUST be displayed raw (up to 50 KB).
- **FR-012**: Changelog display MUST NOT block or fail the update if parsing fails — a warning is shown and the update continues.
- **FR-013**: `CHANGELOG.md` files larger than 50 KB MUST be truncated and a "(changelog truncated)" note appended.
- **FR-014**: When `--json` is active, changelog entries for each updated resource MUST be included in the output object as a `changelog` string field.

### Key Entities

- **SkillManifest**: The parsed front matter from a `SKILL.md` file. Fields: `name`, `description` (optional), plus arbitrary extension fields preserved as-is.
- **CatalogEntry** (generated): An entry in `SKILLS.md` — `category`, `name`, `description`, `source_path`.
- **ChangelogEntry**: A single versioned section from `CHANGELOG.md` — `version`, `date`, `body`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `sth catalog init` generates a `SKILLS.md` that is immediately consumable by `sth list` — zero manual edits required after generation, verified end-to-end.
- **SC-002**: `sth new` produces a `SKILL.md` that passes `sth catalog init` discovery on the first run — zero structural errors in the scaffold output.
- **SC-003**: For every bundle that includes a `CHANGELOG.md`, changelog entries are displayed during `sth update` when a previous version is known — 100% display rate for conforming changelogs.
- **SC-004**: Changelog display never blocks or errors a successful update — 0 update failures attributable to changelog parsing.
- **SC-005**: `sth catalog init` processes a repository with 100 skills across 10 categories in under 5 seconds.

---

## Assumptions

- The v2 state schema from spec 005 is in place (specifically `previous_version` per resource, required for changelog diffing).
- The bundle's managed file inventory from spec 006 is in place (required for `sth catalog init` to know which files belong to which resource).
- `SKILL.md` front matter uses YAML-style key-value pairs (`key: value`), consistent with the existing catalog format.
- The canonical changelog format targeted by the parser is [Keep a Changelog](https://keepachangelog.com/) v1.0.0. Other formats are displayed raw without error.
- "Entries since previous_version" means changelog sections with a date or version later than the `previous_version` install. If versions cannot be compared (non-semver tags), all entries are shown.
- `sth catalog init` is intended for use in skills repositories, not in consumer project directories. Running it in a consumer project is not an error but will typically produce an empty catalog (and exit with the "No skills found" message).
- OSC 8 clickable links (for SKILLS.md URLs in terminal output) are out of scope for this spec.
